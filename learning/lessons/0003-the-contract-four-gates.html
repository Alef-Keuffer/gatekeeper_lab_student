W1. What is the gatekeeper’s job?

  1. Fix wrong records before they reach storage.
  2. Label each record with how much trust.
  3. Score the model’s confidence in each record.
  4. Compute the consequence of using each record.

What “the contract” means in code

Part A is the first of the five parts the lab’s README.md splits the work into: A contract, B evidence, C semantic findings, D acceptance policy (decide()), E reflection. Each has its own test class (PartA, PartB…) and a banner comment in gatekeeper.py. The starter’s TODOs are numbered after them: A1 is ExtractedValue’s rule, A2 is Relationship’s.

In lesson 2 the contract was the step that refuses to build a malformed or inconsistent record. In code it is just two pydantic classes, ExtractedValue and Relationship. Calling Relationship(**data) either returns an object or raises ValidationError. There is no half-built record.This is Alexis King’s “Parse, don’t validate”: make illegal states unrepresentable, so every later function can trust what it receives.

Pydantic checks the input in a fixed order. Think of it as four gates:

GateWhat it looks atError type you seeGiven or built
1. Unknown fieldsany key the class doesn’t declare, because of model_config = ConfigDict(extra="forbid")extra_forbiddengiven
2. Each field alonethe type (Predicate enum, bool, str | None), presence, and Field(min_length=1)enum, missing, string_too_short, bool_parsinggiven

Gates 1 and 2 run together and pydantic reports all their errors at once. Gate 3 runs only if gates 1 and 2 found nothing. So a record with an empty subject_text and causes + negated=True reports only string_too_short; your _negation rule never gets a say.Confirmed by running your code with pydantic 2.14. The docs say after-validators “run after the whole model has been validated” (Validators › Model validators).

The two functions you wrote

class ExtractedValue(BaseModel):
    model_config = ConfigDict(extra="forbid")           # given
    value: str | None                                    # given: no default
    status: ValueStatus                                  # given
    reason: str | None = None                            # given

    @model_validator(mode="after")                       # built from here down
    def _value_matches_status(self) -> "ExtractedValue":
        if self.status == ValueStatus.PRESENT and self.value is None:
            raise ValueError("status present requires a value")
        if self.status != ValueStatus.PRESENT and self.value is not None:
            raise ValueError(f"status {self.status.value} forbids a value")
        return self

Three choices to defend

mode="after", not "before". An after-validator receives self: an object whose fields have already passed gate 2. So self.status is a real ValueStatus even if the input was the string "present", and self.negated is a real bool even if the input was "yes". A before-validator gets the raw input dict and would have to handle strings, missing keys and junk itself.

raise ValueError, not assert. Pydantic turns a ValueError raised in a validator into a ValidationError with type value_error, like any other contract failure. An assert would work in tests, but Python deletes asserts when run with python -O, and the contract would silently vanish.Validators › Raising validation errors warns against assert for exactly this reason. An after-validator must also return self.

Unknown is not null. value: str | None has no default, so leaving value out is an error (missing). You must write value=None and a status that says why it is empty: not_found_in_source, ambiguous, withheld… A bare None can’t tell “the paper doesn’t say” from “the extractor crashed”. That design is given; your validator enforces it in both directions, which is what test_every_non_present_status_forbids_value pins.

Two limits to name before you’re asked

  • value="" passes as present. The check is is None, and an empty string isn’t None. No test covers it. (Confirmed by running.)
  • The gates guard construction only. Relationship isn’t frozen and has no validate_assignment, so rel.negated = True on a causes record succeeds silently. Rebuilding it with Relationship.model_validate(rel.model_dump()) raises. (Confirmed by running.)

Practice: which gate stops it?

For each input, pick the first gate that rejects it, or say it gets built. Every answer was confirmed by running your code.

1. ExtractedValue(value="", status="present")

  1. Accepted: the record exists
  2. Rejected: an unknown field
  3. Rejected: a rule fails
  4. Rejected: a field fails

"" is a valid str, and your rule only asks self.value is None. This is limit 1 above: a present-but-empty value gets through.

2. ExtractedValue(status="withheld")

  1. Rejected: a rule fails
  2. Accepted: the record exists
  3. Rejected: a field fails
  4. Rejected: an unknown field

value has no default, so it is required: missing · Field required. “Unknown is not null”: you must write value=None explicitly.

3. ExtractedValue(value="Germany", status="not_found_in_source")

  1. Rejected: a field fails
  2. Rejected: a rule fails
  3. Rejected: an unknown field
  4. Accepted: the record exists

Both fields are fine alone. Your second if raises: value_error · Value error, status not_found_in_source forbids a value.

4. The Gene X record, but with predicate=causes, negated=True and subject_text="".

  1. Rejected: a rule fails
  2. Accepted: the record exists
  3. Rejected: an unknown field
  4. Rejected: a field fails

It breaks the negation rule too, but gate 3 only runs once every field is valid. The only error reported is string_too_short on subject_text.

5. ExtractedValue(value=None, status="present", confidence=0.9)

  1. Rejected: a field fails
  2. Rejected: a rule fails
  3. Rejected: an unknown field
  4. Accepted: the record exists

confidence isn’t declared, so extra="forbid" gives extra_forbidden. The present-without-value rule would also fail, but it never runs.

6. A Relationship with predicate=inhibits and negated="yes".

  1. Rejected: a rule fails
  2. Rejected: a field fails
  3. Accepted: the record exists
  4. Rejected: an unknown field

Pydantic’s lax mode turns "yes" into True, so gate 2 passes. Then _negation sees True + inhibits and raises. Lesson 2’s surprise, now with its mechanism.

7. Why do the validators raise ValueError instead of using assert?

  1. assert cannot carry an error message
  2. ValueError runs faster than an assert
  3. assert is removed under python -O
  4. pydantic forbids assert inside any validator

Optimised mode strips every assert, so the contract would silently stop checking. assert can carry a message, and pydantic does accept it, but its docs advise against it.

8. rel was built with causes, negated=False. Then a later step runs rel.negated = True. What happens?

  1. ValidationError is raised at the assignment
  2. The assignment succeeds with no error
  3. Python raises AttributeError: model is frozen
  4. The predicate silently changes to unrelated_to

Validators run when the object is built, not when it changes. Neither frozen=True nor validate_assignment=True is set, so the record now breaks the rule and nothing notices. Limit 2.

9. What does mode="after" give your validator?

  1. It runs even when fields fail
  2. It sees raw input before parsing
  3. It runs again on every assignment
  4. It sees typed fields, already checked

self.status is already a ValueStatus and self.negated a bool, so a plain comparison is enough. Raw input is what mode="before" sees, and question 4 showed it doesn’t run when fields fail.
