Two passes: your rules only run on clean fields

A repair of lesson 3. One idea, six questions, five minutes. You leave able to predict exactly which errors a ValidationError lists.

What went wrong last time

Questions 4 and 5 tested the same thing, and lesson 3 buried it under too much else. That’s on the lesson, not on you. Also, two of its answer labels overlapped: confidence is “a field”, and it does “fail”. This lesson names the error type instead.

The one idea

Forget the four gates. Pydantic makes two passes over the input:

PassAsks, for every keyError type
1. Each key aloneDoes the class declare this key? Is a declared key present? Is its value the right type and size?extra_forbidden, missing, enum, string_too_short
2. Your rulesDo the fields agree with each other? (your @model_validator(mode="after"))value_error

Two facts, and they are the whole lesson:

  1. Pass 1 never stops early. It checks every key and lists all its errors together.
  2. Pass 2 runs only if pass 1 found nothing. If any key failed, your rule never runs, even if it would also have failed.

Why? Your rule reads self.status and self.value as real, typed values. If status was "maybe", there is no valid self.status to compare, so pydantic doesn’t call the rule at all.The docs: after-validators “run after the whole model has been validated” (Validators › Model validators). Lesson 3’s gates 1 and 2 are pass 1; gate 3 is pass 2.

A pass-1 error names the key it’s about. A pass-2 error names no key: your rule is about the whole object. The first example shows fact 1 (two errors at once). Add confidence=0.9 to the second example and you get only extra_forbidden: fact 2.

Try it yourself from the repo root, in the venv where the tests pass:

python -c "from gatekeeper import ExtractedValue as E; E(value=None, status='present', confidence=0.9)"

Practice: what does the error list?

For each call, pick every error type the ValidationError lists. (none) means the object gets built. All confirmed by running your code.

1. ExtractedValue(value="Germany", status="maybe", confidence=0.9)

  1. enum
  2. extra_forbidden
  3. enum + extra_forbidden
  4. enum + value_error

Both are pass-1 errors, and pass 1 lists all of them. Fact 1.

2. ExtractedValue(value=None, status="present")

  1. value_error
  2. missing
  3. extra_forbidden
  4. (none)

Every key is declared and valid alone (None is allowed by str | None), so pass 2 runs, and your first if raises.

3. ExtractedValue(value=None, status="present", confidence=0.9)

  1. value_error
  2. extra_forbidden + value_error
  3. extra_forbidden
  4. (none)

This is lesson 3’s question 5. confidence isn’t declared, so pass 1 fails, and your rule never runs. Fact 2.

4. ExtractedValue(value=None, status="withheld", reason="privacy")

  1. missing
  2. value_error
  3. extra_forbidden
  4. (none)

reason is declared (optional), and a non-present status with no value is exactly what your rule wants. Built.

5. ExtractedValue(status="present")

  1. value_error
  2. missing
  3. missing + value_error
  4. (none)

value has no default, so leaving it out is a pass-1 error. Pass 2 never runs. Leaving a key out is not the same as writing value=None.

6. A Relationship with predicate=causes, negated=True and subject_text="".

  1. value_error
  2. string_too_short + value_error
  3. (none)
  4. string_too_short

Lesson 3’s question 4. Same rule, other class: the empty string fails min_length=1 in pass 1, so _negation never gets a say.
