Owning the Gatekeeper · Lesson 2

Foundations: the job, three kinds of wrong, and who wrote what

Lesson 1 used words before it explained them. This lesson lays the ground floor. About ten minutes, mostly practice.

The job

An LLM reads scientific papers and turns sentences into records such as Gene X · causes · Disease Y. The records go into a database that people will rely on. The LLM can be wrong while its output looks perfect.This is OWASP’s LLM09 Misinformation: “false or misleading information that appears credible.”

The gatekeeper is the code between the LLM and the database. For each record it decides how far the database should trust it. It never fixes a record; it gives the record one label, its disposition:

DispositionPlain meaning
QUARANTINEset aside and unusable: its evidence quote isn’t really in the paper
HUMAN_REVIEWa person must look at it before anyone uses it
PROVISIONALstored and usable, but flagged as not fully trusted
AUTHORITATIVEstored as trusted fact
REJECTrefused outright; it exists in models.py, but your decide() never returns it

Three kinds of wrong

To sort any bad record, ask one question: what do I have to look at to see the mistake?

KindYou see it by looking atExampleCaught by
Malformedone field alonepredicate="prevents" (not in the vocabulary), negated="maybe", an empty subject_text, an unknown extra fieldfield types and Field(…) limits → ValidationError
Inconsistentthe whole record, without the paper: two fields break a rule that links themcauses with negated=True; value="Germany" with status=NOT_FOUND_IN_SOURCEthe model validators → ValidationError
Consistent-but-falsethe record and the paperGene X: causes with negated=Falsethe checks → findings → decide()

The first two kinds never become a record at all: building the object raises ValidationError. That “refuse to build” step is the contract. The third kind passes the contract. Only a check that compares the record with the paper can see it.Every row was confirmed by running your code. One surprise: pydantic accepts negated="yes" as True, so "yes" is not malformed. "maybe" is.

The Gene X sentence, three ways

The sentence: “Gene X did not significantly increase the risk of Disease Y.”

predicatenegatedWhat the record claimsContract
unrelated_to or uncertainTruea denied or unclear link, which is faithful to the paperaccepts
causesTruebreaks the lab’s rule: a negated record may not carry an asserting predicate (see below)rejects (inconsistent)
causesFalse“Gene X causes Disease Y”: coherent, and falseaccepts (consistent-but-false)

The last row is what the model actually returned. It has two mistakes: causes (the paper denies an effect) and negated=False (the sentence says “did not”). With only the first mistake you get the middle row, which the contract rejects. Making both mistakes produces a record that breaks no rule, so it gets through. The professor’s test name says exactly this: test_two_consistent_mistakes_pass_the_contract.

Wait: doesn’t causes + negated=True just mean “does not cause”?

In plain English, yes. That is a fair objection, and it depends on what negated means, which the lab never defines in words. There are two possible readings:

  • A flag on the predicate (“NOT causes”). Then causes + negated=True reads “does not cause”, which is fine. But unrelated_to + negated=True reads “not unrelated”, a double negative.
  • A flag on the sentence (“the source says this negatively”), with the predicate stating on its own what the record claims. Then causes + negated=True is a mismatch: the predicate claims causation from a sentence that denies it.

The professor’s rule (reject negated=True with any predicate in ASSERTED) and test (test_negated_unrelated_or_uncertain_ok accepts unrelated_to + negated=True) only make sense under the second reading. That is my inference from the rule and the tests, not something the lab states, so ask the professor to confirm it. A designer has a good reason to choose it: predicate is the field everyone filters on. A query for predicate = 'causes' that forgets to check negated would return Gene X as a causal claim. With the rule, causes in the database always means a positive claim.A second reason: “did not significantly increase the risk” is not the same as “does not cause”. A non-significant result usually shows only an absence of evidence; see Altman & Bland, “Absence of evidence is not evidence of absence”, BMJ 1995. So even “does not cause” would overstate the paper, and uncertain is arguably closer.

That’s why this kind is called inconsistent rather than “contradictory”: the record breaks a rule the lab chose. It isn’t illogical in plain English.

Two inputs that are not evidence

Consequence: how bad it would be if this record were wrong. The gatekeeper doesn’t work this out. It is a parameter, decide(rel, report, consequence), and whoever calls decide() supplies it. Nothing in the lab computes it; the tests pass Consequence.LOW or Consequence.HIGH by hand. It describes where the data will be used, not the record.An illustration, not from the lab: a literature-browsing tool might be LOW, a database feeding clinical decisions CRITICAL. Ask the professor how Chapter 2 frames who sets it.

Confidence: the model grading its own answer (the uncertainty field). In your code it has one effect. uncertainty_finding turns HIGH or UNKNOWN into a HIGH_CANDIDATE_UNCERTAINTY warning, which is copied into the decision’s reason_codes for a reviewer or an audit. No rule acts on it. The model can be confidently wrong (Gene X said low), and letting it move the disposition would let it grade its own homework. README design rule 3 forbids that, and test_model_confidence_is_not_authority enforces it.

Questions 1–5: sort each record into one of the three kinds of wrong, or “faithful” if nothing is wrong. Answer from memory; your first click counts.

You can see it from that one field: prevents isn’t in the Predicate vocabulary. Pydantic refuses to build the record: Input should be 'associated_with', 'causes', … [type=enum].

2. The Gene X sentence. The model returns predicate=inhibits, negated=True.

  1. Malformed
  2. Inconsistent
  3. Consistent-but-false
  4. Faithful

Each field is valid alone, but together they break the lab’s rule: a negated record may not carry a predicate from ASSERTED, and inhibits is one of them. You don’t need the paper to see it. Your _negation validator raises, so the record never exists.

3. “Gene A variants were associated with a higher incidence of Disease B.” The model returns predicate=causes, negated=False.

  1. Malformed
  2. Inconsistent
  3. Consistent-but-false
  4. Faithful

The record is coherent, but the paper reports an association, not causation, and only the paper shows that. Your Part E check causal_claim_finding flags it as ASSOCIATION_AS_CAUSATION, and at LOW consequence decide() returns PROVISIONAL.

4. ExtractedValue(value="Germany", status=NOT_FOUND_IN_SOURCE)

  1. Malformed
  2. Inconsistent
  3. Consistent-but-false
  4. Faithful

The status says “not found in the source”, yet a value is filled in. The two fields contradict each other. Your _value_matches_status validator raises.

5. Same Gene A sentence as question 3. The model returns predicate=associated_with, negated=False.

  1. Malformed
  2. Inconsistent
  3. Consistent-but-false
  4. Faithful

This is exactly what the paper says. No check fires, and decide() returns AUTHORITATIVE at LOW consequence (confirmed by running your code).

6. Where does the consequence value come from?

  1. decide() computes it from findings.
  2. The model reports it alongside.
  3. The caller passes it in.
  4. required_assurance() derives it from assurance.

It is a parameter of decide(). It describes where the data will be used, so the gatekeeper can’t work it out from the record. required_assurance() goes the other way: consequence → assurance.

7. In your code, what does uncertainty=high actually do?

  1. It sends the record to review.
  2. It adds a warning, nothing else.
  3. It quarantines the record at once.
  4. It lowers the required assurance level.

uncertainty_finding returns a HIGH_CANDIDATE_UNCERTAINTY warning, which lands in reason_codes. No rule in decide() reacts to it, so the disposition is the same as with low.

8. Which of these did the implementation write, rather than receive from the professor?

  1. The decide() rule list
  2. The Finding model type
  3. The consequence-assurance mapping table
  4. The causal-claim check function

Part E asked for “one new check”, and the README didn’t say which. Choosing association-reported-as-causation, its cue words and its wiring into rule 3 were all implementation decisions. The rule list and the mapping were in the starter docstrings; Finding is in models.py.

9. verify_span also rejects an end_offset past the end of the text. Where did that rule come from?

  1. Added by the implementation itself.
  2. The starter docstring required it.
  3. A public test demanded it.
  4. The EvidenceSpan model enforces it.

The starter docstring listed only two conditions: the checksum matches, and the slice equals the quote. Python slices clamp silently, so "abc"[1:10] == "bc" would pass. The implementation added the bound; REFLECTION.md records it under “Changed”. EvidenceSpan can’t check it because it never sees the text.

Say it out loud

Three sentences, without looking: what the gatekeeper is for, why Gene X gets past the contract, and who sets the consequence. Then check.

Checklist: three points
  1. It sits between the LLM and the database and gives every record a disposition: how far the record can be trusted. It labels records; it doesn’t fix them.
  2. Gene X has two mistakes that agree (causes + negated=False), so the record breaks no rule. Only comparing it with the paper shows it’s false.
  3. The caller sets the consequence, according to where the data will be used. The gatekeeper never computes it.
